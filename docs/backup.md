# Backup: export everything, import it back

**Where:** Settings (the gear at the bottom of the sidebar), **Data controls**: the exports as buttons and the import file picker (`docs/settings-dialog.md`).

## Export
- `GET /api/export` (or "Export all chats"): **one JSON file** with every conversation, which can be imported again:
  ```json
  {"format": "chitchat-backup", "version": 2, "exported_at": "...",
   "conversations": [{"id", "title", "settings", "created_at", "updated_at", "leaf", "pinned", "archived",
                      "messages": [{"role", "content", "meta", "created_at", "parent"}]}]}
  ```
  Oldest chat first. Message `meta` carries what the page shows (reasoning, usage, tool calls, notes). Whether a chat is pinned or archived is in the file (`pinned`, `archived`, true or false). **Every version** of every message is in the file (`docs/branching.md`): `parent` is the position in the list of the message a message follows (null for the first), `leaf` the position of the last message of the path that was showing. Version 1 files (no `parent`, no `leaf`) import as one straight path.
- `GET /api/export?format=full` ("Export with attachments"): a **zip** with `chats.json` (the same document) and `attachments/<id>` for every file the chats mention. It is built in a temporary file and streamed, not held in memory. A file that is gone from disk is left out, and the import says so for that message. The JSON also carries your `custom_instructions` (one text), in this zip and in the plain JSON export. So do the `defaults` for new chats (Settings, General: model, thinking effort, tools).
- `GET /api/export?format=md` ("Export as Markdown"): a **zip with a Markdown file per conversation**, named `date-title-idprefix.md` (the id prefix is why two chats with the same title don't collide). Meant for reading, not for importing. Each file reads as the one-chat Markdown export does (`docs/round-9.md`).
- The export of one chat (settings dialog) is the path showing, without the other versions (and without `parent` and `leaf`), and its JSON can be imported too. The Markdown zip is the same: the path showing.
- Never in an export: OpenAI's encrypted compaction items (opaque, tied to a model, only for the model). Attachment **files** are only in the zip with attachments; the JSON and the Markdown list them by name.

## Import
`POST /api/import` (multipart `file`), or "Import chats from a file". It takes the JSON backup, the zip with attachments (told apart by its first bytes, not its name), a single chat's export, or a bare list of chats.
- **Nothing is overwritten.** A conversation whose `id` is already here is skipped, so importing the same file twice does nothing ("Nothing new: 1 chat already here"), and importing an old backup next to newer chats never touches them. A chat without a usable id (a file written by hand or by another tool) gets a new one, so it is added again each time. Ids that aren't 32 hex digits are replaced, never used.
- **All or nothing.** The whole file is checked first (shape, roles, sizes), and the inserts are one transaction: a file with one bad conversation adds none of them, and an error halfway rolls everything back. Refusals say why in plain words ("conversations.1.messages.0.role: Input should be 'user' or 'assistant'"), as a 422; a file over 50 MB is a 413.
- **Versions are checked.** With a `leaf` in a chat, each `parent` must be an earlier message of that chat (so no loops and no dangling parent) and `leaf` must be one of the messages, or the whole file is refused with a message saying which chat. Without a `leaf` the messages are one path.
- **Limits:** 5,000 conversations, 20,000 messages in one, 1,000,000 characters in a message.
- **What is kept and what isn't.** Titles (trimmed, 200 characters, "Imported chat" if blank), messages in order, timestamps (any ISO form, normalized to UTC; missing ones default to the chat's), settings (validated; tools this version doesn't have are dropped, and settings that are still invalid give the defaults rather than a refusal). From `meta`, only a whitelist is kept: reasoning, usage counts, tool calls (with a known status and object-shaped details), `stopped`, `incomplete`, `trimmed`. **Attachments** come back only from the zip (below); from a JSON file they are dropped, and the message gets a note ("[Attached when this was sent, not included in the import: cat.png]") so it isn't a silent loss; compaction is dropped.
- **Files from the zip are checked, not trusted.** For each attachment a message lists, the file `attachments/<id>` is read (never more than the largest allowed size, whatever the zip claims), its type is decided again from its **bytes** with the same rules as an upload (an executable, an empty file or an image over 10 MB is refused), and it is stored under a **new id**; the kind, type and size in the JSON are not believed, and the name is cut to its last path part and 200 characters. The importer only ever opens members whose names it builds from a 32-digit hex id, so a member called `../x` is never used. A file that is missing or refused is left behind with the same note as above. Versions of one message that share a file share the restored file. A chat that is skipped (already here) has no files written. Limits: the zip 1 GB, its `chats.json` 50 MB, all files together 2 GB.
- **Still all or nothing, files included:** files are written first, then the chats and their attachment rows go in one transaction; if anything fails the files written so far are removed again.
- **Custom instructions** in the file are taken **only if you have none** (nothing is overwritten), and ignored if they are longer than the setting allows. The import answer says `custom_instructions: true` when they were taken; the dialog says "custom instructions added".
- **Defaults for new chats** (`defaults`: `model`, `reasoning_effort`, `tools`) follow the same rule: taken **only if none are chosen here**, tools this version doesn't have are dropped, and anything that doesn't fit (a bad effort, an empty model, not an object) is ignored. The import answer says `defaults: true` when they were taken, the dialog says "defaults for new chats added", and the page takes them at once (the Settings controls, and the tools of a new chat on screen).
- **Why the whitelist:** the page renders `meta`. A crafted file must not be able to make a conversation unopenable or run script. Beyond cleaning the data, the page now draws a tool call whose details it can't use as a plain line ("Used web_search") instead of failing the whole conversation, which also protects against older saved shapes. Titles are set as text and replies go through the sanitizer, as always; the tests import a file full of markup, `javascript:` links and malformed tool details and check nothing runs.
- Imported chats are searchable at once (by title and by message) and can be continued like any other.

## Not covered
- A separate copy of the database before an upgrade is a different thing: `docs/round-6.md`.
- Merging two versions of the same chat: a chat that exists is skipped whole.
- Importing the Markdown zip or another app's format (ChatGPT's export would need a converter).

Tests: `tests/test_backup.py` (52: both exports, round trip into a fresh database, idempotency, never overwriting, hostile and malformed files, atomicity, limits, metadata cleaning), `tests/ui/test_backup_ui.py`.
