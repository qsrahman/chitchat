# More tools: calculator, search_chats, fetch_url, get_datetime, read_chat, read_attachment

Six tools were added to the registry from phase 7 (`app/tools/`). They need no API key. Each conversation has its own switches, and all of them are in the **Tools** menu (wrench icon, left of the text box), a checkbox each with a one-line hint. Web search used to have a globe of its own in the composer; it is in the menu now, so the composer has one tools control and every tool is named in words where it is chosen (`docs/ui-review.md`). `GET /api/tools` lists every usable tool as `{name, label, hint}`. The loop, the per-reply call cap (`MAX_TOOL_CALLS`), the guidance added to the instructions while a tool is on, and the UI line per call all work as described in `docs/phase-7.md`.

## On by default
A new chat starts with every tool **except web search** switched on (`store.DEFAULT_TOOLS`: calculator, search_chats, fetch_url, get_datetime, read_chat, read_attachment). Web search stays off because each search costs money and needs a key. They are the default for *new* chats only: an existing chat keeps the tools it was saved with, and each chat's Tools menu still switches any of them off for that chat. The list is app-wide and is the `tools` of the defaults for new chats (`docs/settings-dialog.md`): until someone chooses otherwise it is this list; **choosing no tools is kept** (`PUT /api/defaults` with `{"tools": []}`), and the Settings switch for web search changes only web search, leaving the others as they are.

**"Not chosen" is stored as such.** `PUT /api/defaults` changes only the fields it names, and `null` puts one back to not chosen; the Settings page sends only what the user changed. (The first version of this saved every default whenever one changed, tools included, so touching the thinking effort froze the tools at "none", and the Tools menu of every new chat looked switched off. A record saved by that version, with `tools: []` and no `"v": 2` mark, is read as not chosen; any later record is exact. `store.stored_defaults` says how.) The backup exports the defaults as stored (`tools: null` while not chosen) and imports them only where none are chosen. The list is spelled out, not "every tool that exists", and a test fails when a tool is added to `NAMES` without a decision about it here: a tool that can change things must never be on by default.

What it costs: every request carries the six tools' definitions and guidance (about 1,000 tokens), and `fetch_url` can read any public page the model decides to fetch, with the protections described below. The browser tests start with none on (`tests/ui/conftest.py`) so that a reply doesn't echo the tools; the tests about the default say so.

## calculator
Exact arithmetic: models are unreliable at long multiplication, percentages and compound interest, and the answer shows in the reply as `17 * 23 = 391`.
- The expression is parsed with `ast` and walked by a small evaluator that accepts only numbers, `+ - * / // % **`, parentheses, `pi`, `e`, `tau` and a list of `math` functions (`sqrt`, trig, `log`, `exp`, `gcd`, `factorial`, `comb`, `perm`, `round`, `min`, `max`...). Names, attributes, calls to anything else, strings, comparisons and comprehensions are refused, so nothing reaches the interpreter. (No dependency covers this; `eval` is not an option.)
- Bounded: expressions over 500 characters, integer results over 10,000 bits, `**` that would exceed that (checked before computing, so `9**9**9` is an error and not a hang), `factorial`/`comb`/`perm` over 1,000, complex results and infinities are errors. Division by zero and domain errors are reported to the model, which can correct itself.
- `^` is XOR in Python, so it is refused with a message to write `**`. Floats are shown to 15 significant digits (`0.1 + 0.2` is `0.3`).

## search_chats
The model searches your saved conversations (`store.search_conversations`, the phase 8 FTS5 index) when you refer to something said before ("what did we decide about X?"). It returns the best match from each matching conversation with its title, date, who wrote it and a longer snippet (up to 6). In the UI the matches are links to those chats. Past messages can contain pasted web pages, so the result is labelled as information, not instructions. It searches the user's *other* conversations: the chat it runs in is already in front of the model, so it is left out. A tool that needs to know which chat it runs in declares `per_chat=True` and takes a `conversation_id`; the route binds it for each reply with `tools.bound_to`, so the shared tool object is never changed. Titles are searched too (a title-only match is reported as such).

## fetch_url
Reads one web page or PDF: the readable text, 12,000 characters at a time (about 3,000 tokens). The usual follow-up to a search result.

**Long pages come in parts.** The tool has an `offset` argument (null for the start). A page longer than one part ends with "[The page continues: call fetch_url again with offset=N to read on (M more characters).]", and the model passes that N to get the next part. Each part says which characters it is ("characters 12,000 to 24,000 of 128,038"); concatenating the parts gives the whole text exactly, with nothing lost or repeated (tested). The page is fetched again for each part (the tool keeps no state), and the UI shows "12,000 characters read from character 12,000 of 128,038; there is more".

**PDFs** (`application/pdf`) are read as text with the same `pypdf` code the attachments use (`attachments.pdf_to_text`), the first 100 pages, in a worker thread. A PDF may be up to 10 MB (a PDF is much bigger than the text in it) and is refused, not read half, above that; a pages limit, a scan with no text, a password-protected or malformed file each give a clear error. The title shown is the file name. pypdf parses untrusted files here, bounded by the size, page and time limits, which is the same exposure an uploaded PDF already is.

It is the one tool that makes this server connect to an address a model chose, so it is built defensively (all in `_fetch`, `app/tools/fetch.py`):
- **Public sites only.** Scheme must be `http`/`https`, no `user:pass@`, ports 80 and 443 only. The host is resolved, and **every** address it resolves to must be public (`ipaddress.is_global`, not multicast; IPv4-mapped IPv6 is unwrapped). That refuses loopback, private ranges, link-local (including cloud metadata at `169.254.169.254`), CGNAT, reserved and unspecified addresses, in IPv4 and IPv6. One private answer among public ones is a refusal.
- **The check is the connection.** The request goes to the checked IP with the real name as `Host` and TLS SNI (`extensions={"sni_hostname": ...}`), so DNS can't answer differently between the check and the connect (DNS rebinding), and certificates still verify against the real name (confirmed live against `example.com`).
- **Redirects are followed by hand** (at most 3), each hop going through the same checks, so a public page can't bounce the server to `127.0.0.1`.
- **No ambient authority:** a fresh client per call, no cookies, no `Authorization`, `trust_env=False` (so proxy variables can't route around the pinning), fixed `User-Agent`.
- **Bounded:** 1 MB of body (read as a stream and stopped, also for compressed responses), 15 seconds in all, text types only (`text/*`, JSON, XML, XHTML); images, PDFs and downloads are refused.
- **Untrusted output:** the text is labelled as untrusted internet content that must not be obeyed, and the guidance tells the model to cite the URL. The UI shows the title as text and links the URL only if it is `http(s)`.
- HTML is reduced to text with the stdlib `html.parser`: scripts, styles, navigation, footers, asides and forms are dropped, headings and paragraphs keep their breaks.

Not covered: pages that need JavaScript to show their content (you get what the server sent), logins and paywalls, scanned PDFs (no OCR), and a page over 1 MB of HTML (cut there, and it says so).

## get_datetime
The time of day, another timezone, and how long until or since a date: things the default prompt's date (to the day, in the server's time) cannot answer, and models are bad at ("how many days until...", "what time is it in Tokyo").
- Arguments: `timezone` (an IANA name, or null for the server's own: where the person using a local app is), `days_from_now` (the date that many days ahead or back, ±36,500) and `until` (an ISO date or time: how long until or since it, in days, hours and minutes, and the calendar days). All three are required but may be null, which is what OpenAI's strict mode asks.
- A date or time without a zone is read in the zone asked for; one with a zone (`...Z`, `+02:00`) is that instant. `days_from_now` keeps the wall-clock time, so a change of clocks in between is not counted as a day more or less.
- `zoneinfo` and `datetime.fromisoformat` do the work, nothing is hand-parsed. A zone that doesn't exist (or isn't a valid key, such as `../etc`) is an error that says to use an IANA name. The clock is `clock._now`, replaced in tests.
- In the UI: "Monday 5 October 2026, 14:03 · PKT, UTC+05:00", opening to the extra lines as text.

## read_chat
Opens one of the user's other saved conversations, which `search_chats` can only point to: the model quotes, continues or summarizes a past chat instead of guessing from a snippet. `search_chats` results now carry each conversation's id (`(id ..., date)`), which is what `read_chat` takes.
- It reads the path the user last read (`store.list_messages`), not every version, as `[3] assistant: ...` lines with the files attached (`(attached: schema.sql)`), 12,000 characters at a time. It pages by message, like `fetch_url` pages by character: a part ends with "[The conversation continues: call read_chat again with from_message=N ...]", and the parts together are every message once (tested).
- One message is cut at 4,000 characters with a note ("[message cut: 46,000 more characters]"), so a pasted file or a long answer can't fill a part alone.
- Like `search_chats` it is per-conversation (`per_chat=True`): reading the chat it runs in is an error ("already in front of you"). An unknown id, a chat with no messages and a `from_message` past the end each say so. The id is only ever a bound parameter.
- Past text can hold pasted web pages, so the result says it is information and must not be obeyed. In the UI the call links to the chat (the title as text, the href `#id`).

## read_attachment
Reads a file attached earlier in this conversation. Only the newest message's files go to the model with a turn (`docs/round-3.md`); older ones are a note saying so. With this tool on, the model can list the files of the chat and read one, in parts of 12,000 characters (`offset`, as for `fetch_url`), instead of asking the user to attach it again, and it can read the later part of a long PDF.
- `name` null lists the files (name, kind, size, oldest first); a name (any case) reads that file, the newest of that name if there are several. A name that matches nothing is an error that lists the names, so the model corrects itself.
- Text files and PDFs only: a PDF is read as text whatever `OPENAI_PDF_INPUT` says (`attachments.for_model` with `"text"`, the same code and cache as sending it). An image is an error: a tool result is text, and the model sees an image only while it is attached to the latest message. A file gone from disk is an error too (`attachments.UNAVAILABLE`).
- It sees this conversation's files only (`store.conversation_attachments`), never another chat's: that is tested. File text is labelled as information, not instructions.

## Tests
`tests/test_tools_local.py` (about 130 cases: the calculator's accepted and refused expressions and limits; chat search; fetch_url's address checks for 20+ non-public addresses, redirects into private places, ports, schemes, content types, size and time limits, pinning, malformed HTML), `tests/test_tools_reading.py` (get_datetime with a fixed clock, read_chat and read_attachment: order, paging, limits, errors, isolation between chats), `tests/test_tool_calls.py` (listing, per-conversation switching, guidance, the reading tools bound to a conversation), `tests/ui/test_tools_ui.py` (the menu, which now scrolls when seven tools with a hint each are taller than the room above the composer, and how each call reads). Live (`-m live`): the real model using the calculator, and a real fetch of `example.com` through the pinned connection.

## Future tools (noted, not built)
Roughly in order of value, as decided on 2026-10-05 (when `get_datetime`, `read_chat` and `read_attachment` were built). Each is a module in `app/tools/` plus its UI line in `static/tools-ui.js`, except where it says otherwise. Anything keyless and read-only fits the way tools work today (per chat, untrusted output labelled, and on by default only if it can't change anything); the ones that need more say what.
1. **`run_python`**: running code for data work, exact maths, parsing and charts: the biggest capability jump left, and the only one that needs a real design. Model-written code must not run unisolated on this machine: either a sandbox of our own (a subprocess with no network, a timeout, memory and file limits, a temporary directory, and tests for escape attempts like the SSRF tests of `fetch_url`) or OpenAI's hosted `code_interpreter` (per-session cost, runs on their side, OpenAI only). Its own phase.
2. **Notes or memory** (`remember`, `recall`): the model saves a short fact ("I use metric") that later chats can see. It overlaps with custom instructions, so it must be visible and editable in Settings and never silent; it changes what the model is told, so the user has to stay in control.
3. **Unit conversion**: easy and keyless (`pint`-like tables or a small hand-written set). Currency needs live rates from an API and is left out unless wanted.
4. **`weather`** (and similar one-shot lookups): Open-Meteo needs no key. Reachable through `web_search` already, so this is faster and steadier rather than new.
5. **`lookup_wikipedia` / `search_arxiv`**: short citable reference lookups from free APIs without keys.
6. **File output and image generation**: a generated CSV or Markdown file the user downloads (pairs with `run_python`, which needs somewhere to put results); image generation needs same-origin image serving (the sanitizer strips `<img>`), a new event type, storage and a cost note.
7. **Local notes or files search**: a read-only, allowlisted folder indexed with FTS5, like `search_chats`.
8. **Showing an older image again**: `read_attachment` refuses images (a tool result is text); a tool that re-attaches one to the next request would need `llm.py` to accept image parts in tool output.

Left out on purpose until the app has sign-in (`PLAN.md` phase 9): anything with side effects or credentials (shell, file writes, email, calendar). A confirmation UI for tool calls does not exist either. MCP is a way to get many of the above at once with the same trust problem: looked into in `docs/mcp.md` (feasible as a local client, about one phase, wanting sign-in and a confirmation UI first).
