# Round 5

Three changes: a sweep for flaky tests, a render time budget, and branching. Each is its own commit.

## 1. Flaky-test sweep
**Method.** The suite ran 12 times in a row with six CPU-burning processes competing for the machine (`yes > /dev/null`), then again after each round of fixes (10, 14, 18 and 20 runs). Every failure was read, not retried. Normal runs of 844 tests had been green for weeks; under load 3 of the first 12 runs failed, and the failures were different tests, all UI tests, all with the same shape: the test acted before the page or the server was ready.

**What was wrong, and the fix for each:**
- **The page was "open" before its scripts had run.** `open_app` waited for the heading, which is plain HTML. The module scripts are deferred, so under load a `fill` or an Enter could land on a page with no handlers yet (the message was never sent, the search never ran). `app.js` now sets `data-ready` on `<body>` once the first conversation is loaded and the message box has been focused, and the test `page` fixture waits for it after every `goto` and `reload` (also `open_app` and the axe pages). This was the root of several failures (`test_stop_button_keeps_partial_reply`, `test_no_match_says_so`). The second needed a closer look: the first version of the signal fired as soon as the handlers were attached, and `test_no_match_says_so` still failed about once in 15 runs when 14 copies ran at once. Logging the search box's events showed a `focus` and a `blur` and no `input`: the page's start-up code (`openConversation`) ends with `input.focus()` after its first `GET /api/conversations`, and under load that landed between Playwright focusing the search box and typing, so "zzzz" went into the message box. The signal now waits for that focus. After the change 70 parallel copies of the test passed. (It is also a small real behavior: the page takes the focus when it has loaded, which a very fast user could notice; I left it.)
- **"The reply is there" was not "the reply is saved".** 44 places waited for `Reply #N` to appear and then navigated, searched or reloaded; the text shows before the server has saved the message, so a quick enough next step aborted the stream (Stop semantics) or searched before the chat existed. Each now also waits for the message's action buttons, which appear when the reply is saved. Three search tests waited for the assistant's placeholder, which exists before the request does; they wait for the title or the saved reply now.
- **A disabled button.** The web search toggle is disabled until the page knows which tools exist; one test focused and pressed it too early.
- **Enter went to a link.** After clicking a chat in the sidebar the message box is focused last; the draft test pressed Enter once its text was there but before the focus, so Enter activated the link.
- **Five `sleep(0.1)`s** in the API tests (fixed in round 4: the fake model now says when it is hanging).

**Result:** 20 runs in a row under the same load, 844 passed each time. That is not proof there are none left: the rate before was about 1 failed run in 4, so 20 clean runs make a flake at that rate very unlikely, but a rarer one could still be there. The sweep script is not in the repository (a shell loop with `yes` burners); the method above is all it is.

## 2. A render time budget
`docs/rendering.md` showed that a reply that is one huge block gets none of the block reuse and can keep the main thread busy for most of the stream. `messages.schedule` now caps that: after a render that took longer than 16 ms, the next render of the same message waits twice as long as that one took (a `setTimeout`, then the usual animation frame). Rendering is thereby limited to about a third of the main thread, which leaves the rest for scrolling and the Stop button. Renders under 16 ms, which is every ordinary reply, are not delayed. `render` and so `renderFresh` clear any pending wait, so the end of a stream always renders at once and the saved reply is the full one.

Measured with `scripts/bench_render.py`: the time the main thread is blocked while a huge block streams drops by 55 to 60 percent (28.5 s to 11.5 s for a 20,000-line code block; table in `docs/rendering.md`), and ordinary replies are unchanged. The longest single freeze is not shortened, and the stream finishes up to 15 percent later (the stream itself is not delayed, only what is drawn).

Tests (`tests/ui/test_incremental_render_ui.py`): with every render made to cost 40 ms, a 1.5 s stream renders about 12 times, not 35 (33 renders when the budget was switched off, checked), and the last line of the block is on the page; and an 80-paragraph reply still renders about once per paragraph.
